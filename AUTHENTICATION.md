# Аутентификация и управление доступом

Документ описывает текущую реализацию входа и ролевой авторизации OfficeCooking.Web.
Он не содержит реальных логинов, хешей паролей, cookie, токенов или персональных данных.

## Общая схема

Учётная запись привязана к существующему участнику готовок в таблице `users`. Отдельная
сущность пользователя для входа не создаётся. Для включения доступа администратор назначает
участнику логин, пароль, роль и включает флаг разрешения входа.

Публичными остаются только:

- `GET /health` — проверка процесса;
- `GET /ready` — проверка процесса и PostgreSQL;
- `POST /api/v1/auth/login` — вход.

Остальные маршруты `/api/v1` требуют действующую серверную сессию.

## Роли

Роли иерархические: каждая следующая включает возможности предыдущей.

| Роль | Возможности |
| --- | --- |
| `viewer` | Просмотр пользователей, шаблонов, готовок и балансов |
| `editor` | Всё из `viewer`, создание и редактирование готовок, предварительные расчёты |
| `admin` | Всё из `editor`, изменение пользователей и шаблонов, управление логинами, паролями и ролями |

Frontend скрывает недоступные разделы, но это только удобство интерфейса. Окончательная проверка
прав всегда выполняется backend для каждого запроса.

## Где хранятся учётные данные

В PostgreSQL, в таблице `users`, находятся следующие поля:

- `username` — нормализованный логин;
- `password_hash` — хеш пароля, но не сам пароль;
- `role` — `viewer`, `editor` или `admin`;
- `auth_enabled` — разрешён ли вход.

Пароль хешируется алгоритмом `scrypt` с индивидуальной случайной солью. Текущие параметры:
`N=16384`, `r=8`, `p=1`, результат 32 байта. Одинаковые пароли получают разные хеши.
Исходный пароль восстановить из сохранённого значения нельзя.

Пароли не записываются в frontend, `localStorage`, конфигурационные файлы, журналы или Git.
Минимальная длина нового пароля — 12 символов.

## Сессии

После успешного входа backend генерирует криптографически случайные session-token и CSRF-token.
В PostgreSQL, в таблице `auth_sessions`, сохраняются только SHA-256 digest этих токенов, идентификатор
пользователя и время истечения. Оригинальный session-token существует только в cookie браузера.

Cookie `office_cook_session` имеет атрибуты `HttpOnly`, `SameSite=Strict` и `Path=/`. JavaScript
не может прочитать эту cookie. В production дополнительно обязателен атрибут `Secure`, поэтому
сессия передаётся только через HTTPS.

Постоянная авторизация не используется. Cookie не получает `Expires` или `Max-Age` и удаляется
браузером при завершении его работы. После следующего запуска браузера пользователь вводит логин
и пароль заново. Серверная запись дополнительно имеет абсолютный срок жизни 12 часов, поэтому
даже в постоянно открытом браузере потребуется повторный вход. Срок задаётся настройкой
`OFFICE_COOK_SESSION_TTL_HOURS` и ограничен диапазоном от 1 до 24 часов.

## CSRF-защита

Для команд `POST`, `PUT` и `PATCH` backend требует заголовок `X-CSRF-Token`. Значение берётся
frontend из отдельной cookie `office_cook_csrf` и сверяется с digest в серверной сессии.
Одной session-cookie недостаточно для выполнения изменяющего запроса со стороннего сайта.

Дополнительно изменяющие запросы принимаются только с JSON Content-Type. Запросы `DELETE` в
текущей версии API запрещены.

## Создание и изменение доступа

Первый администратор назначается локальной CLI-командой после применения миграций:

```powershell
cd backend
uv run office-cook-auth list-users
uv run office-cook-auth set-user --legacy-id <id> --username <login> --role admin
```

Пароль вводится интерактивно и не попадает в историю shell. После первого входа администратор
управляет остальными учётными записями на странице **«Доступы»**. По умолчанию там показываются
только уже настроенные записи; нового человека можно выбрать в выпадающем списке и добавить
кнопкой `+`.

Изменение логина, пароля, роли или состояния доступа отзывает все существующие сессии этого
пользователя. Отключение `auth_enabled` также делает ранее выданные cookie недействительными.
Обычный выход удаляет текущую серверную сессию и обе cookie.

## Развёртывание

Публичная установка запускается через `compose.prod.yaml`: Caddy завершает TLS, frontend nginx
отдаёт React-приложение и проксирует API, а FastAPI и PostgreSQL не публикуют порты наружу.
На endpoint входа действует ограничение частоты запросов. Production-конфигурация backend не
запустится без secure-cookie.

Для публичной установки обязательны HTTPS, закрытый порт PostgreSQL, длинный случайный пароль
БД, резервные копии и защита доступа к `.env`. Секреты, дампы и реальные данные нельзя добавлять
в Git.
